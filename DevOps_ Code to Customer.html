Part 1 · The problem

Dev and Ops wanted opposite things

new-feature.zip
DEVELOPMENT

Goal: ship new features fast

Rewarded for change. Writes code, then hands it over.

“It works on my machine!”
Wall of confusion
OPERATIONS

Goal: keep systems stable

Rewarded for uptime. Every change is a risk.

“Your code broke production!”

Before DevOps, most companies had two separate teams. Development writes features and is rewarded for change. Operations runs the servers and is rewarded for stability, so every change looks like a risk.

Developers finished code and threw it over the wall to Ops, often with little documentation. When it failed in production, each side blamed the other. This barrier is often called the wall of confusion.

Ask the room: whose fault is it, Dev or Ops? Answer: neither. The wall is the problem.

Part 1 · The problem

Five problems the wall created

Slow releases

Features waited months for a big release.

Manual deploys

A checklist run by hand. One missed step, one outage.

Late bugs

Testing came last, so users often found bugs first.

Blame game

Energy went into finding who, not fixing how.

Long downtime

No monitoring, so failures took hours to find.

1. Slow releases: features were bundled into big releases every few months. 2. Manual deployments: someone followed a checklist by hand; one missed step meant an outage. 3. Bugs found late: testing happened at the end, when bugs are most expensive, and customers often found them first. 4. Blame game: separate teams with separate goals. 5. Long downtime: without automation and monitoring, finding and fixing a failure took hours or days.

DevOps grew out of the need to fix exactly these problems.

Part 2 · What DevOps is
Dev+Ops=DevOps

DevOps is a culture, a set of practices and tools that bring development and operations together to deliver software faster and more reliably.

The first DevOpsDays conference was held in Ghent, Belgium, in 2009, organised by Patrick Debois.

DevOps is not a product. It combines two words and two teams: Development and Operations.

Definition: a culture, set of practices and tools that unify development and IT operations, so one team can deliver software faster and more reliably. The people who build software and the people who run it share responsibility for the result, and automate the path between writing code and serving users.

History: Patrick Debois organised the first DevOpsDays in Ghent, Belgium, in 2009, and the term spread from there.

Part 2 · Myths vs facts

DevOps is a way of working, not a tool

DevOps is a tool you install→A way of working; tools support it
DevOps is only a job title→Everyone shares ownership of the product
DevOps means only automation→Culture and feedback matter as much
Only big tech companies need it→Any team that ships software benefits

You cannot buy or install DevOps. Jenkins, Docker and Kubernetes support DevOps, but a team using them while still working in silos is not doing DevOps.

"DevOps Engineer" is a real job title, but the practice belongs to everyone: developers, testers and operations. Automation is a big part, but collaboration and feedback matter just as much. And it is not only for large companies: a three-person team or a college project benefits from the same habits.

CALMS is credited to early DevOps advocates John Willis, Damon Edwards and Jez Humble.

CALMS is a checklist to see whether a team is really doing DevOps.

Culture: shared responsibility, no blame. After a failure ask "what in our process allowed this?", not "who did this?". Automation: builds, tests, deployments and server setup run without manual steps. Lean: deliver in small batches; small changes are easier to test and roll back. Measurement: track numbers such as how often you deploy and how fast you recover. Sharing: share knowledge, dashboards and tools across teams.

If one pillar is missing, the roof is weak.

Compare the same company before and after adopting DevOps. Big, infrequent releases become small, frequent ones. Manual checklists become an automated pipeline that runs the same steps every time. Small changes plus monitoring mean problems are spotted quickly and rolled back.

Phase 2 · Code

Phase 2, Code. Git is a version control system: it records every change to every file, who made it and why, and lets you go back to any earlier version.
Diagram: main holds the stable code. A developer creates a feature branch, makes commits, then opens a pull request (merge request on GitLab). A teammate reviews it and it is merged into main.
Four beginner commands: git clone downloads a repository, git add stages changes, git commit saves a snapshot with a message, git push uploads commits. Git is the tool; GitHub, GitLab and Bitbucket host repositories and add reviews and collaboration. Linus Torvalds started Git in April 2005 after the free licence for BitKeeper, then used for the Linux kernel, was withdrawn.

Phases 3 and 4. Build turns source code into something that can run, called an artifact. Java projects use Maven or Gradle to compile and produce a .jar or .war file; JavaScript projects use npm to install packages and create a bundle. Build tools also download the libraries the app depends on.
Test: automated tests run on every build. The test pyramid shows the healthy balance: many fast unit tests at the bottom (JUnit for Java, PyTest for Python), fewer integration tests in the middle, and a small number of slow UI tests at the top (Selenium drives a real browser). SonarQube scans code for bugs, vulnerabilities and code smells and can stop poor code moving forward.

CI/CD: from commit to production

Continuous IntegrationMerge often; every change is built and tested automatically

      
Continuous DeliveryEvery passing change is ready to release; a person approves

      
Continuous DeploymentEvery passing change goes to production automatically

    

  

  
CI/CD is the automated assembly line at the heart of DevOps.
Continuous Integration: developers merge code into the shared branch often, and every merge triggers a build and the tests, so breakages show up within minutes. Continuous Delivery: every change that passes is packaged and ready; a person approves the release to production. Continuous Deployment: no manual approval; every change that passes all checks goes live automatically.
The software that runs this line is a CI/CD server. Two of the most popular are Jenkins and GitHub Actions, compared next.

Hudson was created by Kohsuke Kawaguchi. GitHub Actions is free for public repositories; private repositories get included minutes per plan.

  

  
Both are CI/CD tools doing the same job: run build, test and deploy steps automatically. A project normally uses one.
Jenkins: open-source automation server. It took the name Jenkins in January 2011 after a community vote, forking from Hudson, which Kohsuke Kawaguchi created. You install and maintain it, extend it with plugins, and write pipelines in a Jenkinsfile using a Groovy-based DSL. Works with any Git host.
GitHub Actions: CI/CD built into GitHub, generally available since 11 November 2019. No server to install; jobs run on GitHub-hosted runners or your own self-hosted runners. Workflows are YAML files in .github/workflows. Free for public repositories; private repositories get included minutes per plan.
Rule of thumb: code already on GitHub and want a quick start, use GitHub Actions. Need full control or a non-GitHub repository, use Jenkins.







  

    
Phase 5 · Release
Same pipeline, two tools

    

      

        
JenkinsJenkinsfile


pipeline {  agent any  stages {    stage('Build') {      steps { sh 'mvn compile' }    }    stage('Test') {      steps { sh 'mvn test' }    }    stage('Deploy') {      steps { sh './deploy.sh' }    }  }}

      

      

        
GitHub Actions.github/workflows/ci.yml


name: CIon: [push]jobs:  build:    runs-on: ubuntu-latest    steps:      - uses: actions/checkout@v4      - name: Build        run: mvn compile      - name: Test        run: mvn test      - name: Deploy        run: ./deploy.sh

      

    

    
1 · Build2 · Test3 · Deploy

  

  
The same three-step pipeline written for both tools; the highlight walks through Build, Test and Deploy in both files at once.
Jenkinsfile: "pipeline" is the whole job, "agent any" runs it on any available Jenkins machine, and each "stage" runs a shell command. GitHub Actions: "on: [push]" runs the workflow on every push, "runs-on: ubuntu-latest" picks a GitHub-hosted Linux runner, "actions/checkout" fetches the code, and each "run" is a shell command.
The commands are identical (mvn compile, mvn test, ./deploy.sh); only the wrapper changes. Learn the idea once and you can use either tool. Ask: which file looks easier to read?

Phase 6, Deploy, part one. "Works on my machine" happens because the laptop and the server have different language versions, libraries or settings. Docker packages the app together with everything it needs.
A Dockerfile is the recipe. docker build turns it into an image, a read-only template built in layers (watch them stack). docker run starts a container from the image: a running, isolated instance. One image can start many identical containers on a laptop, a test server and production. Images are stored in a registry such as Docker Hub.
Containers share the host's operating system kernel, which makes them lighter than virtual machines. Docker was open-sourced in March 2013 by dotCloud, now Docker, Inc.

Google announced Kubernetes in June 2014 and donated it to the new Cloud Native Computing Foundation in 2015. The name is Greek for helmsman; K8s counts the 8 letters between K and s.

  

  
Docker runs containers on one machine. Real applications need many containers across many machines. Kubernetes manages that for you.
A cluster is a group of machines. The control plane is the brain (api-server, scheduler, etcd, controller-manager); worker nodes run the workloads. A pod is the smallest unit and wraps one or more containers. You declare the desired state in YAML, for example "run 6 copies", and Kubernetes keeps reality matching it. Watch the demo: a pod crashes and a replacement is scheduled automatically. That is self-healing. It also scales pods up and down and performs rolling updates.
Facts: announced by Google in June 2014, version 1.0 in July 2015, donated to the CNCF in 2015. The name comes from the Greek for helmsman or pilot.

Phase 7, Operate. Infrastructure as Code means describing servers, networks and databases in files that live in Git, get reviewed and can be reused, instead of clicking through a cloud console.
Terraform by HashiCorp provisions infrastructure. You write .tf files in HCL saying what should exist, run terraform plan to preview and terraform apply to create it. It works with AWS, Azure, Google Cloud and many other providers and keeps a state file of what it created. In 2023 HashiCorp changed Terraform's licence; the community fork OpenTofu is now hosted by the Linux Foundation.
Ansible configures servers once they exist: installs packages, creates users, copies configuration, deploys the app. It is agentless: it connects over SSH, so nothing extra needs installing on the managed servers. Tasks are written in YAML playbooks. Created by Michael DeHaan (first release February 2012), acquired by Red Hat in 2015.
Together: Terraform creates the empty servers, Ansible makes them ready to run the app.

Phase 8, Monitor. Once the app is live you need to know how it behaves, ideally before users notice a problem. The chart is simulated: when latency crosses the 300 ms line, an alert fires.
Prometheus pulls (scrapes) metrics from applications at regular intervals, stores them as time series, and is queried with PromQL. Grafana (first released 2014 by Torkel Ödegaard) builds dashboards on top. Alertmanager routes alerts to email, chat or on-call phones. Logs are a separate stream: the ELK stack (Elasticsearch, Logstash, Kibana) collects and searches them.
Google's SRE book defines four golden signals: latency, traffic, errors and saturation. Prometheus started at SoundCloud in 2012 and became the CNCF's second hosted project after Kubernetes in 2016. Monitoring closes the loop: what you learn feeds the next Plan.

After git push, every step runs automatically. Step 3 is the same job whether the team uses Jenkins or GitHub Actions.

  

  
Follow one change, for example a bug fix, from a laptop to production.
1. The developer commits and runs git push. 2. The code reaches GitHub; a pull request is reviewed and merged. 3. The merge triggers the CI/CD pipeline in Jenkins or GitHub Actions, whichever the team uses. 4. The pipeline builds with Maven and runs the tests. 5. If tests pass, it builds a Docker image and pushes it to a registry. 6. Kubernetes performs a rolling update to the new image. 7. Prometheus and Grafana watch the new version; if errors rise, an alert fires and the team rolls back.

DORA stands for DevOps Research and Assessment. Bars are illustrative only.

  

  
How do you know DevOps is working? The DORA research programme (DevOps Research and Assessment) tracks four key metrics. Two measure speed: deployment frequency and lead time for changes. Two measure stability: change failure rate and failed deployment recovery time (previously called mean time to recover).
Good teams improve speed and stability together; they are not a trade-off. The bars on screen are illustrative only.
